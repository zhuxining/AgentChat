# AgentChat 产品蓝图

版本：v0.2
状态：讨论稿

## 1. 文档目的

本文定义 AgentChat 的产品定位、目标用户、要解决的问题、核心体验和阶段方向，回答“为谁解决什么问题、产品如何创造价值”。

本文不定义技术选型、进程、数据库、通信协议、编程语言或部署方式；这些内容由《系统架构文档》说明。

本文根据产品讨论重新组织。尚未验证的假设和待决策事项会明确标出，不视为已确认需求。

## 2. 产品定位

AgentChat 是一种**按角色组织 Agent 能力、重新设计人与 Agent 协作方式的产品**。

用户面对的不是模型、工具和聊天入口的集合，而是一组职责清楚、可以持续协作的数字分身。例如，用户可以找 Obsidian 知识管家整理已有知识库，找投研助手研究和跟踪标的。每个角色可以连接适合自己的模型、工具和既有工作环境；用户优先按“这件事该找谁”来使用能力，而不是先理解“该打开哪个工具”。

一句话定位：

> AgentChat 将分散在模型、工具和工作环境中的 Agent 能力，按用户理解的角色组织起来，让用户以更自然的方式找到、委托并持续协作。

“像通讯软件”描述的是一种熟悉的交互载体，不是产品边界或最终定位。

## 3. 产品愿景

用户可以拥有一组各自擅长不同领域、能够持续演化的数字分身。用户按角色直接与它们协作，不必亲自管理底层模型和工具，也不必把所有任务塞进一个能力模糊的通用助手。

AgentChat 逐步连接用户已有的工作环境和外部 Agent 能力，让用户可以通过稳定的角色使用它们；未来，专业分身之间可以互相委托任务，形成更完整的数字团队。

## 4. 核心问题与产品假设

### 4.1 核心问题

当用户想完成一项工作时，往往不知道应该找哪个 Agent、使用哪个工具、从哪里开始。现有 AI 体验通常围绕单个聊天入口或单个工具组织，用户需要自己理解能力差异、选择入口、补充上下文并追踪后续工作。

### 4.2 产品假设

如果把能力按用户熟悉的职责角色组织，并允许用户直接选择专业分身或从事情本身开始，那么用户就能更容易找到适合的能力、委托工作并持续协作，而不必先成为 Agent 管理专家。

**需要验证的关键假设：** 用户是否更容易通过角色发现并使用合适的 Agent 能力；角色是否比模型/工具名称更符合用户的心智模型，并带来更好的协作体验。

## 5. 目标用户

### 第一目标用户：个人重度 AI 用户

典型特征：

- 经常使用 AI 处理工作或个人事务；
- 已在使用多个模型、Agent、应用或工作环境；
- 需要研究、知识管理、写作、规划、整理或执行等不同类型的能力；
- 不一定具备配置、组合和管理 Agent 的能力或意愿；
- 希望能力服务于自己的实际工作，而不是被迫迁移全部资料和流程。

可能人群包括独立开发者、产品经理、研究人员、内容创作者、自由职业者和小型创业者。此名单是候选用户群，不代表已完成细分验证。

### 后续探索用户：家庭和小团队

未来可能需要共享部分数字分身、任务和知识，同时保留个人边界。第一阶段不以大型企业组织管理或公共社交网络为目标。

## 6. 产品原则

1. **先角色，后工具：** 用户首先按职责理解能力，底层模型和工具不应成为主要选择负担。
2. **专业分身可直达：** 用户知道找谁时，应能直接使用专业分身，不必经过主分身。
3. **事情也可作为入口：** 用户不知道找谁时，可以先表达要做的事，由产品帮助其找到合适角色；具体路由和确认策略仍需验证。
4. **个体独立演化：** 每个专业分身是在特定领域持续演化的个体，保有自己的身份、上下文和记忆；不通过跨分身共享记忆来制造一个趋同的集体助手。
5. **接入既有工作环境：** 目标是让角色使用用户现有的资料、工具和工作流，而不是要求用户先迁移到 AgentChat 自有空间。
6. **管理复杂度不转嫁给用户：** 多数用户不擅长管理 Agent。系统应承担必要的配置与团队维护工作，避免让用户频繁审批或调参。
7. **透明且可控：** 用户应能理解角色职责、正在处理的工作、所用能力和关键变化；涉及权限边界或高影响操作时应保留适当控制。
8. **协作而非单轮问答：** 对话可以承载持续工作、任务委托和跟进，而不把所有过程隐藏在一次性聊天回复中。

## 7. 产品概念模型

### 7.1 数字分身（Agent）

数字分身是用户可以理解和协作的角色化能力单元，具有明确的领域职责、工作方式、可用能力和记忆边界。用户可以使用产品提供的常见角色，也可以创建自己的分身。

数字分身不应只是换了名称的通用提示词；角色需要让用户知道适合交付什么工作、如何协作以及能力边界在哪里。

### 7.2 专业分身

专业分身是用户面向具体领域直接协作的角色，例如 Obsidian 知识管家、投研助手。它在自身职责和记忆范围内持续演化，并可连接相关模型、Agent 能力、工具和用户已有工作环境。

### 7.3 主分身

主分身是帮助用户照看数字团队的观察者和团队教练，不是所有工作的必经入口，也不是替代专业分身的万能助手。

在用户授权的产品边界内，主分身可以观察团队的对话与任务过程，帮助用户改进分身团队。它可以发现职责、方法或协作上的问题，并推动相关分身分别演化；**观察团队不意味着合并或跨分身共享记忆**。团队改进是降低用户管理负担的后台机制，不是产品面向用户的核心价值本身。

关于主分身具体能修改哪些设置、哪些变化自动生效，需依据风险和用户控制原则进一步设计；不应预设用户需要为日常改进频繁审批。

### 7.4 能力与工作环境

能力包括 Agent、模型、工具以及访问用户已有资料和应用的方式。它们是角色完成工作的手段，不应成为用户必须自行编排的主要对象。

“连接已有工作环境”是长期方向，候选范围包括本地知识库（如 Obsidian）、其他 AI 工具（如 ChatGPT、Codex）及用户日常使用的其他应用。具体接入顺序、接入深度和可行边界尚待验证，不代表第一阶段全部支持。

### 7.5 会话与任务

会话是用户与一个或多个数字分身持续协作的空间。任务是从协作中形成、可跟进的工作单元，可以包含执行状态、结果和后续处理。二者服务于角色协作，而不是产品的独立价值终点。

### 7.6 记忆

记忆是单个分身在其明确范围内积累的上下文。每个分身的记忆保持独立，不默认向其他分身开放或复制。主分身可以观察团队表现，但团队观察与记忆共享是不同权限。

## 8. 核心使用场景

### 场景一：直接找到专业角色

用户想整理自己的知识库，直接进入 Obsidian 知识管家，要求整理近期笔记、找出关联内容。分身在用户已有环境中工作，并在自己的职责范围内积累对用户偏好的理解。

### 场景二：按事情找到角色

用户只描述想完成的工作，不确定该找哪个分身。AgentChat 帮助用户发现合适角色；用户也可以改为直接选择角色。两种入口并存，不要求用户始终通过主分身路由。

### 场景三：与专业分身持续协作

用户将一个研究主题交给投研助手，逐步补充问题、查看阶段结果并继续追问。协作可以跨会话或设备延续，具体任务执行和主动跟进能力按阶段建设。

### 场景四：创建自己的分身

用户从常见角色开始，也可以按自己的领域和工作方式创建、调整分身。创建流程应让不熟悉 Agent 配置的用户也能建立可用角色；配置复杂度和自动生成程度待验证。

### 场景五：主分身帮助改进团队

主分身观察用户与不同分身的协作，帮助发现角色职责、工作方法或团队分工中的问题，并推动相关分身各自改进。主分身不把一个分身的领域记忆自动复制到其他分身。

### 场景六：专业分身之间协作（未来方向）

复杂工作可由一个分身将子任务委托给另一个专业分身，再把结果带回原协作过程。用户能理解谁负责什么、结果如何汇总；开放式、任意 Agent 互相通信不属于默认前提。

## 9. 核心交互模式

AgentChat 同时支持两种入口：

- **角色入口：** 用户明确知道要找谁，直接进入相应专业分身。
- **事情入口：** 用户先说要做什么，再由产品协助找到适合的角色；是否自动委托、何时征求确认，应根据任务风险和用户预期设计。

两种入口围绕同一个原则：**用户不应先理解底层能力编排，才能开始工作。**

沟通体验可以借鉴熟悉的会话列表、单聊、消息、未读和通知，但不能把“像通讯软件”误解成只做聊天壳。交互模式的差异应体现在能力如何被角色组织、工作如何被委托与延续，以及用户如何理解协作过程。

## 10. MVP 与第一阶段范围

### 10.1 MVP 要验证什么

MVP 要验证核心假设：用户是否能通过角色而非工具/模型入口，更容易找到并使用适合的 Agent 能力，完成有意义的工作并愿意持续协作。

MVP 不以“所有工具都已接入”或“完整自治的数字团队已实现”为完成标准。

### 10.2 MVP 的价值闭环

```text
用户有一项真实工作
    ↓
直接选择专业分身，或先描述事情再找到分身
    ↓
分身利用相关能力和既有工作环境开展协作
    ↓
用户理解进展、结果与下一步
    ↓
用户继续使用该角色，或创建/调整适合自己的分身
```

闭环必须完整地解决一个有代表性的工作问题；范围可以狭窄，不要求同时完善多端、复杂群聊、主动监控和任意 Agent 协作。

### 10.3 第一阶段候选能力

以下是围绕核心假设的候选能力，最终范围应由场景选择和验证结果决定：

- 提供少量职责明确的常见专业分身；
- 用户可创建和调整自己的分身；
- 支持直接选择角色，也支持从事情开始发现角色；
- 与至少一个真实工作环境或能力来源形成有价值的连接；
- 支持与分身持续对话，并保留必要的会话上下文；
- 对执行中的工作提供足够的状态、结果和失败反馈；
- 明确分身各自的记忆边界，不默认跨分身共享；
- 由主分身承担团队观察和改进的方向可先通过有限、可理解的方式验证，不要求一开始实现全面自动优化。

**场景选择尚未确定：** Obsidian 知识管家和投研助手是讨论中提出的候选角色，不能仅凭例子认定其中任何一个已被选为 MVP 场景。

### 10.4 暂不作为第一阶段承诺

- 接入所有模型、Agent 和用户应用；
- 任意 Agent 之间的开放通信和自动协作；
- 复杂团队、家庭或企业权限管理；
- 无限制的自主高风险操作；
- 完整的主动监控和复杂定时任务体系；
- 以“管理 Agent 数量”或“自动优化团队”作为用户核心价值。

## 11. 成功标准与验证方向

成功标准应判断角色化组织是否让协作变得更容易，而不只是统计创建了多少 Agent。

### 核心价值信号

- 用户能否快速理解不同角色的职责与边界；
- 用户面对真实工作时，能否找到合适的分身；
- 用户是否愿意直接回到某个专业分身继续协作；
- 用户是否认为角色入口比自己在工具和通用聊天之间选择更省心；
- 用户是否在不具备 Agent 管理经验的情况下，仍能获得有效体验。

### 体验质量

- 角色不能胜任时，用户能否理解原因并找到替代路径；
- 已有资料和工作环境能否在授权边界内被有效利用；
- 长工作能否看到进展、结果和失败原因；
- 分身记忆是否保持清晰、独立且可理解；
- 用户是否能理解主分身观察和团队调整的边界。

具体指标定义、目标值和测量方式待用户研究及场景验证后确定，当前不预设未经验证的数字目标。

## 12. 关键风险与待验证问题

1. **角色是否比工具更好理解？** 用户是否自然按职责找能力，还是仍习惯按应用、模型或任务类型选择？
2. **专业角色如何避免只剩人设差异？** 需要用真实任务证明其职责、工作方式和可用能力存在可感知差异。
3. **用户希望怎样开始？** 角色目录和事情入口都需要存在，但两者的默认权重和路由行为仍待验证。
4. **首个场景该选什么？** Obsidian 知识管理与投研研究依赖不同的数据、工具和质量标准，应按用户可达性、任务频率和结果可判断性选择，而非同时铺开。
5. **已有环境如何连接？** 不同工具的权限、数据访问和工作流差异很大，长期愿景不能直接等同于首发范围。
6. **主分身观察边界如何让用户信任？** 用户认可主分身观察对话和任务，但具体可见范围、用途说明、保留方式和敏感边界仍需设计。
7. **跨 Agent 委托何时有必要？** 它是未来方向，应在单个专业分身的价值成立后再验证，避免过早引入复杂调度。

## 13. 产品蓝图结论

AgentChat 的核心不是聊天窗口、多 Agent 数量或后台自动管理，而是**按角色组织 Agent 能力，降低用户找到并使用合适能力的成本，重新组织人与 Agent 的协作方式**。

- 用户直接与专业分身协作；
- 不确定找谁时，可以从事情出发获得角色帮助；
- 用户可以使用预置角色，也可以创建自己的分身；
- 主分身作为观察者和团队教练，帮助用户改进团队，但不是日常工作的唯一入口；
- 各分身保持独立身份和记忆，不以跨分身共享记忆换取表面上的统一；
- 能力覆盖更多工具和环境、分身之间互相委托，属于逐步验证和扩展的方向。

最终愿景：

> 让用户不必先成为 Agent 专家，就能按熟悉的角色组织和使用分散的智能能力，与一组专业数字分身自然、持续地协作。
